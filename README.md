# שירות שליחת SMS לעובדים

שירות HTTP ששולח הודעות SMS לעובדי הארגון דרך ספק SMS חיצוני (המדומה שמסופק במשימה), שומר כל הודעה ב-SQL Server, מנהל את מחזור החיים שלה (Pending → Sending → Sent/Failed) ומאפשר לשאול על הסטטוס. כולל ממשק Angular פשוט.

- **Backend:** ASP.NET Core 10 (Minimal APIs), EF Core 10, SQL Server 2025
- **Frontend:** Angular 22 (standalone components, signals, zoneless), מוגש ב-nginx
- **בדיקות:** xUnit, FluentAssertions, NSubstitute, Testcontainers (SQL Server אמיתי)
- האפיון המלא שלפיו נבנה הפרויקט: [`SPEC.md`](SPEC.md). מסמך חלק ב': [`docs/PART-B.md`](docs/PART-B.md).

```bash
cp .env.example .env
```

```bash
docker compose up --build
```

| כתובת | מה |
|---|---|
| http://localhost:4200 | ממשק משתמש |
| http://localhost:8080/swagger | Swagger UI |
| http://localhost:8080/health | בדיקת תקינות (API + DB) |

- ה-API מריץ migrations ו-seed של עובדים בעלייה, כך שאין צעדים ידניים.
- **ספק ה-SMS:** כתובת השרת המדומה נקבעת ב-`SMS_PROVIDER_URL` בקובץ `.env` (ברירת מחדל `http://host.docker.internal:5005`, כלומר שרת שרץ על המחשב המקומי בפורט 5005). נתיבי ה-endpoints של הספק נקבעים ב-`SMS_PROVIDER_SEND_PATH` וב-`SMS_PROVIDER_STATUS_PATH` (ברירת מחדל `send` ו-`status/{id}`). אם הספק לא זמין, ההודעות יעברו ל-`Failed` אחרי 3 ניסיונות עם השגיאה המתאימה, וה-API ממשיך לעבוד כרגיל.

## API

| Method | Path | תיאור |
|---|---|---|
| `POST` | `/messages` | `{ "to", "body" }` + Header אופציונלי `Idempotency-Key`. `to` חייב להיות מספר של עובד במערכת, אחרת `400`. מחזיר `202` עם `{ id, status }` ו-`Location`. אותו מפתח עם אותו תוכן מחזיר `200` עם אותו `id`; עם תוכן שונה `409`. |
| `GET` | `/messages/{id}` | סטטוס ההודעה בלבד: `{ id, status }`. לא מחזיר נמען, תוכן, ניסיונות ושגיאות, כי הדרישה היא סטטוס, ואין סיבה לחשוף את פרטי ההודעה לכל מי שמחזיק במזהה. `404` אם לא קיימת, `400` אם ה-id אינו GUID. |
| `GET` | `/messages?status=Sent` | עד 100 הודעות, החדשות קודם. כל פריט מכיל רק `{ id, to, status }`, כאשר `to` **מוסתר חלקית** (`+97250****321`), בלי תוכן, ניסיונות, שגיאות ושמות עובדים. `status` הוא סינון **אופציונלי** ולא תלוי רישיות: בלי `status` מוחזרות הודעות מכל הסטטוסים, וסטטוס לא קיים מחזיר `400`. התשובה עטופה ב-`{ items: [...] }`. |
| `GET` | `/health` | `200` כשה-API וה-DB זמינים, `503` אחרת. |

כל השגיאות מוחזרות כ-`ProblemDetails` (RFC 9457) עם `traceId`. שגיאת פורמט (טלפון לא תקין, תוכן ריק או ארוך מדי, `id` שאינו GUID, סטטוס לא קיים) מחזירה `400` מסוג `ValidationProblem`, עם כל השגיאות לפי שדה (`errors`). מספר תקין שאינו של עובד מחזיר `400` כללי בלבד (`{ "title": "Invalid input" }`). בשני המקרים הפרטים נרשמים גם בלוג השרת.

## הנחות יסוד

1. **השדה `to` הוא מספר טלפון**, ולא מזהה עובד. זה נובע מהדרישה לוולידציה על "מספר טלפון" בקלט. מכיוון שהמערכת שולחת SMS **לעובדים**, המספר חייב להיות שייך לעובד אחד לפחות (בדיקה מול `EmployeePhones`); מספר תקין שאינו של עובד נדחה ב-`400` עם הודעה כללית, "Invalid input" (ראה בטבלת ההחלטות). מספר שמשותף לכמה עובדים מקבל הודעה **אחת**. שמות העובדים לא נשמרים על ההודעה ולא מוחזרים ב-API.
2. **רק מספרי סלולר ישראליים.** הקלט מתקבל בפורמטים `050-7654321`, `0507654321`, `+972507654321`, `972507654321` (כולל רווחים וסוגריים), ונשמר בפורמט E.164 (`+972507654321`).
3. **אורך ההודעה: 1–670 תווים** אחרי Trim, שהם 10 מקטעי Unicode (עברית מחייבת Unicode: 70 תווים במקטע בודד, 67 בכל מקטע בהודעה מרובת מקטעים). מספר המקטעים מחושב ונשמר לצורכי מידע ותמחור.
4. **השליחה אסינכרונית.** `POST` שומר בסטטוס `Pending` ומחזיר `202` מיד. worker ברקע שולח לספק, כך שנפילה או איטיות של הספק לא מפילות את ה-API, וקריסה באמצע לא מאבדת הודעות.
5. **מזהה ההודעה הוא GUID** שנוצר בשרת, כדי שלא יהיה אפשר לנחש מזהים.
6. **נתוני העובדים נטענים מ-seed** (`Data/employees.seed.json`) בעליית המערכת. אין API לניהול עובדים, כי זה לא נדרש.
7. **ה-seed מגיע במבנה "מופעים"**, שורה לכל צירוף עובד+טלפון. בטעינה מאחדים את המופעים לעובד אחד עם כמה טלפונים. ה-seed בטוח להרצה חוזרת (לא יוצר כפילויות).
8. **אין אימות משתמשים ואין Deploy**, בהתאם למשימה.
9. **רק מופע אחד של ה-API רץ**, ולכן worker אחד מספיק. הרחבה לכמה מופעים מתוארת בחלק ב'.
10. **החוזה של הספק משוער** (לא נמסר): `POST {BaseUrl}/send` עם `{ to, message, reference }` שמחזיר `{ id }`, ו-`GET {BaseUrl}/status/{id}`. **הנתיבים ניתנים להגדרה** (`SmsProvider:SendPath`, `SmsProvider:StatusPath`, או `SMS_PROVIDER_SEND_PATH` / `SMS_PROVIDER_STATUS_PATH` ב-`.env`), כך שאם רק הנתיבים שונים, ההתאמה היא בקונפיגורציה בלבד. אם גם מבנה ה-JSON שונה, ההתאמה נוגעת רק ב-`SmsProviderClient.cs`.

## החלטות

| החלטה | למה |
|---|---|
| **פרויקט API אחד** עם Minimal APIs ותיקיות לפי אחריות, ולא Clean Architecture | בהיקף כזה שכבות נוספות הן טקס בלי ערך. ההפרדה היחידה שחשובה היא `ISmsProviderClient`, כי שם צפוי שינוי (ספק שני). |
| **עובדים וטלפונים בשתי טבלאות** (`Employees` עם אינדקס ייחודי על שם+משפחה+כתובת, `EmployeePhones` עם אינדקס ייחודי על עובד+טלפון ואינדקס **לא** ייחודי על הטלפון) | אין כפילות של פרטי עובד, המפתח הטבעי נאכף ב-DB, וחיפוש "של מי המספר" מהיר. רווחים כפולים מכווצים לפני שמירה, כדי ש-"ישראל  כהן" ו-"ישראל כהן" יהיו אותו עובד. |
| **תור בתוך ה-DB** (polling על `Messages`) ולא Message Broker | ה-DB כבר קיים והטבלה היא מקור האמת, כך שאין מצב של "נשמר אבל לא נכנס לתור". `Channel` בזיכרון משמש רק כאות שמעיר את ה-worker מיד; אם האות הולך לאיבוד, ההודעה תישלח ב-poll הבא (תוך שנייה). |
| **מעברי סטטוס רק במתודות של `Message`**, ומעבר לא חוקי זורק `InvalidOperationException` | כל כללי מחזור החיים במקום אחד, קל לבדוק ולהסביר. |
| **`Attempts` עולה ב-`MarkSending`** (בתחילת הניסיון, לא בסופו) | קריסה באמצע שליחה נספרת כניסיון. בלי זה, הודעה שגורמת לקריסה חוזרת הייתה נשלחת שוב ושוב לנצח. מאותה סיבה: הודעה תקועה ב-`Sending` שכבר ניצלה 3 ניסיונות עוברת ל-`Failed` ולא חוזרת ל-`Pending`. |
| **retry רק ב-worker** (3 ניסיונות, backoff של 10 ואז 30 שניות), ו-HttpClient עם timeout של 5 שניות בלבד, בלי retry | מקור אמת אחד לניסיונות, שנשמר ב-DB ושורד קריסה. retry ברמת ה-HttpClient היה מכפיל את מספר הניסיונות בלי שה-DB יודע. |
| **סיווג שגיאות:** timeout, שגיאת רשת, 5xx ו-429 זמניות; שאר ה-4xx קבועות | 4xx אומר שהבקשה עצמה לא תקינה, וניסיון חוזר לא יעזור. |
| **ספק שמחזיר 2xx בלי `id`** נחשב שגיאה קבועה | ייתכן שהספק כבר שלח. ניסיון חוזר עלול לשלוח SMS כפול לעובד, וזה גרוע יותר מהודעה שמסומנת `Failed` ונבדקת ידנית. |
| **`messageId` נשלח לספק כ-`reference`** | אם הספק תומך בכך, הוא יכול לזהות כפילויות (למשל אחרי קריסה). |
| **בדיקת שחזור של `Sending` תקוע** בעלייה, ואחר כך פעם בדקה | בעלייה זה הכיסוי לקריסה. ההרצה התקופתית מכסה גם מקרה שבו השמירה האחרונה ל-DB נכשלה. עם מופע יחיד ו-timeout של 5 שניות, הודעה שנמצאת ב-`Sending` יותר מ-2 דקות היא בוודאות תקועה. **ידוע:** ייתכן שהספק כבר שלח, ולכן ייתכנו כפילויות (ראה חלק ב'). |
| **ולידציית טלפון לפי libphonenumber** (`IsValidNumber` + סוג `MOBILE` + קידומת 972), ולא לפי כלל או regex שכתבתי | הספרייה של Google מחזיקה את טבלאות ההקצאה של כל מדינה, ומבדילה בין נייד לנייח. היא פוסלת בלוקים שלא הוקצו, למשל `050-1xxxxxx`, ולכן מספרי הדוגמה בפרויקט (`050-7654321` ואחרים) נבחרו מתוך בלוקים מוקצים. **ידוע:** אם יוקצה בלוק חדש, הוא יידחה עד שהספרייה תעודכן, ולכן חשוב לעדכן את החבילה באופן שוטף. |
| **הודעות השגיאה של ה-API באנגלית**, והממשק ב-frontend נשאר בעברית | ה-API הוא חוזה שמפתחים ושירותים אחרים צורכים, ואנגלית היא השפה המקובלת בו. התרגום למשתמש הקצה הוא אחריות של ה-UI. |
| **ולידציית פורמט כ-attributes** (`[IsraeliMobilePhone]`, `[SmsBody]` על `SendMessageRequest`), וכללים עסקיים (המספר שייך לעובד, idempotency) ב-`MessageService` | בדיקות פורמט של שדה מתאימות ל-attributes, ורואים אותן ישר על ה-DTO. בדיקה שצריכה DB לא מתאימה ל-attribute, שהוא סינכרוני ולא אמור לגשת ל-DB. ה-attributes קוראים לאותן מחלקות (`PhoneNumberNormalizer`, `MessageBodyRules`) שה-service משתמש בהן, כך שאין שני מקורות לכללים. ה-service ממשיך לבדוק בעצמו, כדי שיהיה בטוח גם כשקוראים לו שלא דרך HTTP. **בגלל זה:** שגיאות פורמט חוזרות לפני הבדיקה מול העובדים, ולא באותה תשובה. |
| **`ValidationFilter<T>` משלנו ולא `AddValidation()` של .NET 10** | המנגנון המובנה מחזיר את שמות השדות בשגיאה כמו ב-C# (`To`), ולא כמו ב-JSON (`to`), גם כשמגדירים camelCase ב-JSON options. זה היה יוצר חוזה לא עקבי מול השגיאות של ה-service. ה-filter מריץ את אותם attributes עם `Validator` הסטנדרטי, בכ-15 שורות. |
| **אותיות במספר נדחות** לפני libphonenumber | אחרת הספרייה ממירה אותיות לספרות ("vanity numbers"), ו-`050ABCDEFG` היה מתקבל. |
| **חישוב מקטעים GSM-7 כולל טבלת ההרחבה** (`€`, `[`, `{` וכו' נספרים כ-2) | כך החישוב תואם את מה שהספק יחייב בפועל. |
| **שגיאות פורמט מפורטות, ושגיאה כללית רק ל"מספר שאינו של עובד"**. שגיאת פורמט מחזירה `ValidationProblem` עם השדות והסיבות. מספר תקין שאינו של עובד מחזיר `{ "title": "Invalid input" }` בלבד (`InvalidInput.Reject` מול `InvalidInput.RejectGeneric`) | שגיאת פורמט לא חושפת שום מידע רגיש, ומי שקורא ל-API צריך לדעת מה לתקן. רק המקרה "המספר לא שייך לעובד" רגיש, כי הודעה מפורשת הייתה מאפשרת לבדוק אילו מספרים שייכים לעובדים בארגון, ולכן רק הוא כללי. הסיבה נרשמת בלוג, עם 3 הספרות האחרונות של המספר בלבד. **ידוע:** `400` כללי בלי `errors` מרמז שהמספר לא של עובד. זה לא מוסיף מידע מעבר להבדל בין `400` ל-`202`, שקיים ממילא (ראה סעיף 9 ב"מה הייתי מוסיף"). |

## מה לא נעשה ולמה

- **סטטוס מסירה (`Delivered` / `Undelivered`):** החוזה של ה-GET של הספק לא ידוע. `GetStatusAsync` קיים ב-`ISmsProviderClient` וממומש לפי החוזה המשוער, אבל ה-worker לא קורא לו. כדי לא להמציא ערכי סטטוס של ספק שלא ראיתי, החלטתי לא לממש את השלב הזה.
- **שרת ספק מדומה משלנו:** לא נבנה, בהתאם לאפיון. הבדיקות משתמשות ב-fake של `ISmsProviderClient`. בדיקה מקצה לקצה מול ספק שעונה בפועל לא נעשתה. אם היה לי עוד זמן, הייתי מרימה ספק מדומה או מוצאת ספק מדומה קיים, ובודקת מולו גם שליחה מוצלחת.
- **אימות, Deploy, CI/CD, Message Broker, Redis:** מחוץ להיקף במכוון.
- **API לניהול עובדים:** לא נדרש. העובדים נטענים מ-seed.
- **Pagination מלא:** יש רק הגבלה של 100 תוצאות. התשובה עטופה ב-`items` כדי שאפשר יהיה להוסיף pagination בלי לשבור את החוזה.
- **בדיקות Frontend ו-E2E אוטומטיות:** הממשק אופציונלי. בדקתי אותו ידנית ובסקריפט Playwright חד-פעמי.
- **ניטור ומטריקות:** יש רק לוגים מובנים. מה הייתי מוסיף מתואר בחלק ב'.

## מה הייתי מוסיף עם עוד זמן

1. התאמה לחוזה האמיתי של הספק, ו-polling של סטטוס מסירה (`Delivered` / `Undelivered`).
2. נעילת שורות ב-SQL (`UPDATE TOP(n) ... WITH (UPDLOCK, READPAST) OUTPUT`) במקום optimistic concurrency, כדי לאפשר כמה workers וכמה מופעים של ה-API.
3. מטריקות (OpenTelemetry): גודל התור, גיל ההודעה הוותיקה ביותר ב-`Pending`, שיעור כישלונות לפי סוג, latency מול הספק.
4. Circuit breaker מול הספק, כדי לא לשרוף ניסיונות כשהוא למטה.
5. Pagination מלא מבוסס cursor.
6. מדיניות שמירה (retention) ומחיקה/התממה של תוכן הודעות ישנות.
7. **שליחה לפי עובד:** אפשרות לשלוח לפי מזהה עובד (שם פרטי + שם משפחה + כתובת, שהם המפתח הייחודי) במקום לפי מספר. ההודעה תישלח לכל המספרים של העובד, אחרי הסרת מספרים כפולים (למשל אותו מספר שהוזן בכמה פורמטים, כמו `050-7654321` ו-`+972507654321`).
8. **Deduplication בקמפיין:** בשליחה לכמה עובדים בבת אחת, מספר שמשותף לכמה עובדים יקבל את ההודעה פעם אחת בלבד. את זה הייתי אוכפת גם במסד הנתונים, עם Unique Index על צירוף הקמפיין ומספר הטלפון (`CampaignId`, `To`), כך שגם בשליחה במקביל או בניסיון חוזר לא תיווצר הודעה כפולה לאותו מספר.
9. **הגנה מלאה מפני חשיפת מספרי העובדים:** השגיאה ל"מספר שאינו של עובד" כבר כללית והרשימה מסתירה את המספרים, אבל ההבדל בין `400` (מספר שאינו של עובד) ל-`202` (מספר של עובד) עדיין מאפשר לגלות, בניסיונות חוזרים, אילו מספרים שייכים לעובדים. הייתי מוסיפה הזדהות ו-rate limiting על `POST /messages`, כך שאי אפשר לנסות מספרים רבים. אפשרות נוספת היא להחזיר `202` גם למספר שאינו של עובד, בלי לשלוח בפועל. בחרתי לא לעשות את זה כרגע, כי מי ששולח בטעות למספר שגוי לא היה מקבל שום אינדיקציה.

## התאמה לארכיטקטורת Microservices

השירות כבר בנוי כשירות עצמאי: אחריות אחת (שליחת SMS ומעקב סטטוס), DB משלו, API מתועד ב-OpenAPI, Docker וקונפיגורציה ממשתני סביבה, `/health`, ו-idempotency, שחשוב כשקוראים לשירות משירותים אחרים שעושים retry. כדי לשלב אותו במערכת microservices, זה מה שהייתי עושה:

1. **נתוני העובדים משירות הבעלים.** כרגע טבלת העובדים נטענת מקובץ seed, אבל במערכת כזו העובדים שייכים לשירות אחר (למשל HR). הייתי מחזיקה עותק מקומי של מספרי הטלפון, שמתעדכן מאירועים (`EmployeeCreated`, `EmployeePhoneChanged`), ולא קוראת ל-API של HR בכל שליחה. כך השירות ממשיך לעבוד גם כש-HR לא זמין.
2. **ממשק אסינכרוני.** קבלת בקשות שליחה מתור (RabbitMQ, Azure Service Bus וכדומה) בנוסף ל-HTTP. ההפרדה ל-`IMessageService` כבר מאפשרת זאת: consumer קורא ל-`SendAsync`. במקום שצרכנים יבדקו סטטוס ב-polling, השירות יפרסם אירועים (`MessageSent`, `MessageFailed`) דרך **Outbox pattern**, כדי שאירוע לא ילך לאיבוד אם השמירה ל-DB הצליחה והפרסום נכשל.
3. **כמה מופעים במקביל.** נעילת שורות ב-worker (סעיף 2 ברשימה הקודמת), הרצת מיגרציות כשלב נפרד בפריסה ולא בעליית האפליקציה, ואפשרות להריץ את ה-worker כתהליך נפרד מאותו קוד, כדי להגדיל כל חלק בנפרד.
4. **אבטחה בין שירותים.** הזדהות (למשל JWT עם client credentials) ו-rate limiting.
5. **Observability.** OpenTelemetry עם tracing ו-correlation id שעובר בין השירותים, מטריקות, והפרדה בין liveness ל-readiness ב-health checks.
6. **עמידות וחוזה.** Circuit breaker מול הספק, וגרסאות ל-API (`/v1/messages`), כדי לשנות את החוזה בלי לשבור צרכנים קיימים.

**מה לא הייתי עושה:** לפצל את השירות לכמה microservices קטנים יותר, למשל ולידציה ושליחה בנפרד. הם חולקים את אותה טבלה ואת אותו מחזור חיים של הודעה, ופיצול היה מוסיף רק קריאות רשת ובעיות עקביות.
